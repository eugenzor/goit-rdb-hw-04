# goit-rdb-hw-04

## Встановлення

Потрібен [uv](https://docs.astral.sh/uv/).

Ініціалізація віртуального середовища
```bash
uv sync
source .venv/bin/activate
```

## Запуск

```bash
python main.py
```

Під час першого запуску датасет завантажується i PostgreSQL запускається локально через `pgserver` у каталозі `.pg_data/`.


## Висновок

Найскладнішим для мене став FULL OUTER JOIN, тому що потрібно врахувати обидва варіанти відсутності відповідного запису. На відміну від звичайного INNER JOIN, такий запит зберігає також штати, представлені лише клієнтами або лише продавцями. Правильне використання COALESCE має значення. Це дає змогу зберегти значення коду штату і чітко визначити кількість.

Найважче було сформулювати бізнес-питання для SELF JOIN. Два продавці можуть жити в одному штаті, але якщо вони працюють у різних містах, їхні результати можуть бути різними. Тому я інтерпретую такий список лише як кандидатів для подальшого регіонального порівняння.

Найкориснішою PostgreSQL-можливістю для production-ETL вважаю ON CONFLICT. Вона дозволяє багаторазово запускати завантаження агрегатів і сегментації без дублювання рядків, одночасно оновлюючи значення, які могли змінитися.

Перевірки якості даних охоплюють відсутні відгуки, порожні тексти коментарів, пропущені категорії товарів, повтори джерельних ідентифікаторів і розподіл статусів замовлень. Фактичні кількості наведені безпосередньо у таблицях вище; такі пропуски не можна автоматично трактувати як нульові оцінки.

Для customer-level ознак я використав customer_unique_id, тому що один покупець може мати кілька customer_id. Інакше число повторних покупок буде занижене. Перед обчисленням seller_score я дедуплікував пари seller_id x order_id та усереднив відгуки за замовленням, щоб кілька товарних позицій не множили одну оцінку.
